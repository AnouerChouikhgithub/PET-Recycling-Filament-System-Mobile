# AI assistant on mobile — step-by-step setup and test guide

Everything you need to **wire the assistant up** and **test the chatbot** on your
phone. Written against the code in this repository as it is now, and against
what was actually observed while building it (every command below was run).

- Web app integration: `../PET-Recycling-Filament-System-Web/docs/ai-agent-web-integration.md`
- Backend agent design: `../PET-Recycling-Filament-System-Backend/docs/ai-agent-design.md`
- Backend API contract: `../PET-Recycling-Filament-System-Backend/docs/api-contract.md`

---

## 0. What you are about to test (read this first)

| The assistant **can** | The assistant **cannot** |
|---|---|
| List your machines | Start, pause, stop or heat anything |
| Read the latest telemetry for a machine | Change a temperature, motor or fan |
| Read recent machine events | Send a machine command of any kind |
| Explain a fault code | Speak to the machine directly |
| Read the machine activity (audit) log | Reach any data that is not yours |

It is **read-only** and it is **not** streaming: one question → one answer
(no typing effect). Its answers are generated by an LLM (Anthropic) on the
**backend**; the phone only ever talks to your Symfony API with your normal JWT.
**No provider key is on the phone, ever.**

## 2. Wire up the backend (this is where it usually breaks)

> The order matters. Steps 2.1–2.3 are the three things that stop the assistant
> from answering; each one was hit for real while building this.

### 2.1 Turn the assistant on — in `.env.local`, not on the command line

Open `PET-Recycling-Filament-System-Backend/.env.local` and add:

```dotenv
AGENT_ENABLED=true
```

Then clear the config cache once:

```bash
cd PET-Recycling-Filament-System-Backend
php bin/console cache:clear
```

**Why not `AGENT_ENABLED=true php -S ...`?** Because PHP's built-in web server
(the one behind `symfony serve` and `php -S`) does **not** copy process
environment variables into `$_SERVER`. Symfony therefore never sees the shell
variable and happily loads `AGENT_ENABLED` from `.env.local` instead. Verified on
this machine:

| How you set it | `getenv()` | `$_SERVER` | Symfony sees |
|---|---|---|---|
| `AGENT_ENABLED=true php -S ...` (web request) | `"true"` | missing | **`.env.local` value wins** |
| `AGENT_ENABLED=true php script.php` (CLI) | `"true"` | `"true"` | `"true"` |

A local `.env.local` is the reliable place — that is also what a real deployment
does. (`AGENT_ENABLED` defaults to **false**: with it off, every assistant route
answers `404 AGENT_DISABLED` and the app shows "Assistant not available".)

### 2.2 Create the assistant tables

The agent needs three tables (`agent_conversation`, `agent_message`,
`agent_token_usage`). They come from a committed migration, but your dev database
may not have it yet — the dev database on this machine **did not**:

```bash
cd PET-Recycling-Filament-System-Backend
php bin/console doctrine:migrations:migrate -n
# verify:
php bin/console dbal:run-sql "SELECT tablename FROM pg_tables WHERE schemaname='public' AND tablename LIKE 'agent%'"
```

Without this, a chat request fails with a 500 (the app shows a generic
"Something went wrong").

### 2.3 Give it a model (only if you want real answers)

```dotenv
# PET-Recycling-Filament-System-Backend/.env.local
ANTHROPIC_API_KEY=sk-ant-...        # never put this in the mobile app
AGENT_MODEL=claude-sonnet-4-5       # default
# AGENT_BASE_URL=                   # only for a proxy/gateway
```

- With a key: real answers, real token usage.
- Without a key: the backend answers `503 AGENT_LLM_UNAVAILABLE` and the app
  shows "The assistant could not generate a response. Please try again."
  (That is a working state — useful for testing the error path.)
- In `APP_ENV=test` the backend uses a deterministic stub instead of Anthropic,
  which is why the automated tests need no key.

Optional knobs (same file):

```dotenv
AGENT_MSG_MAX_CHARS=4000        # per-message limit (the app mirrors it)
AGENT_CONTEXT_MESSAGES=12       # how many past messages the server re-reads
AGENT_DAILY_TOKEN_CAP=200000    # durable per-user daily token budget
AGENT_RATE_LIMIT_MESSAGES=20    # see the caveat below
AGENT_RATE_LIMIT_INTERVAL_SEC=300
AGENT_MAX_TOOL_ROUNDS=4
```

> **Caveat found while testing:** the per-user *message* rate limit is stored in
> `InMemoryStorage` inside `TurnGuard`, which is rebuilt on every request. Under
> a per-request SAPI (`php -S`, php-fpm) it therefore never trips — a 429 from
> that limiter cannot be reproduced locally. The **durable** limit is
> `AGENT_DAILY_TOKEN_CAP` (database-backed), and *that* 429 is what step 4.8
> tests.

### 2.4 Make the backend reachable from the phone

```bash
cd PET-Recycling-Filament-System-Backend
symfony serve --no-tls --allow-all-ip          # or:
php -S 0.0.0.0:8000 -t public public/index.php
```

- `0.0.0.0` matters: bound to `127.0.0.1` the phone cannot reach it.
- Allow the port through Windows Firewall (Private profile) the first time.
- Check the phone can reach it: open `http://<PC-LAN-IP>:8000/api/me` in the
  phone's browser — `{"success":false,"error":{"code":"UNAUTHORIZED",…}}` is the
  correct answer (that means it is reachable and correctly refusing an
  anonymous request).

## 3. Wire up the mobile app

### 3.1 Point the app at your backend

```bash
cd PET-Recycling-Filament-System-Mobile
cp .env.example .env      # if you do not have one yet
```

```dotenv
EXPO_PUBLIC_API_BASE_URL=http://192.168.1.109:8000/api    # your PC's LAN IP
EXPO_PUBLIC_REALTIME_URL=
EXPO_PUBLIC_ENVIRONMENT=development
```

| Where the app runs | What to use |
|---|---|
| Physical phone (Expo Go) | `http://<PC-LAN-IP>:8000/api` — find it with `ipconfig` |
| Android emulator | `http://10.0.2.2:8000/api` |
| iOS simulator | `http://127.0.0.1:8000/api` |

`localhost` on a phone means **the phone**, not your PC — the classic mistake.

### 3.2 Start it

```bash
cd PET-Recycling-Filament-System-Mobile
npm install                # first time only
npm start -- -c            # -c is mandatory after ANY .env change
```

Scan the QR code with Expo Go (Android) or the Camera app (iOS).

### 3.3 Static checks (no phone needed)

```bash
npm run typecheck          # tsc --noEmit, strict
npm test                   # 29 unit tests of the pure logic (Node's test runner)
npx expo export --platform android --output-dir dist   # real Metro bundle
```

### 3.4 Where the assistant lives in the app

| Entry point | Path |
|---|---|
| Machine tab | the **"Ask the AI assistant"** card at the top (sparkles icon) |
| Profile tab | **App → AI assistant** row |
| Route | stack screen `AgentChat` (pushed over the tabs, back arrow returns) |

It reuses the normal signed-in shell: same tokens, same API client, same theme.
It does **not** add a tab and does **not** touch machine controls.

## 4. Test the chatbot — scripted walkthrough

Sign in first (dev fixtures): `anouer@3awedlou.app` / `3awedlou-dev`.

### 4.1 It opens correctly
1. Machine tab → tap **Ask the AI assistant**.
2. Expect: title **AI assistant** / subtitle *Read-only · answers can be out of
   date*; a **data strip** (`<machine> · connected|offline · data 12s old · fresh`);
   the intro card *"Ask about your machine"*; five suggested prompts; a composer
   labelled **Ask the assistant about your machine**.

### 4.2 Suggested prompt
3. Tap **"Show my machines."**
4. Expect: the text lands **in the composer** and the keyboard opens (it does not
   send by itself — you stay in control).

### 4.3 Send a question
5. Press the green **send** arrow (accessibility label *Send question*).
6. Expect in order: your bubble appears on the right (green) → composer clears →
   "Checking your machine data…" with a spinner → the send button is disabled
   while pending → an assistant bubble on the left with the answer, a timestamp
   and any tool pills ("Read the latest telemetry · get_latest_telemetry: 12 row(s)").
7. The suggested prompts disappear after the first turn; **New conversation** and
   **Delete all history** appear in their place.

### 4.4 Follow-up in the same conversation
8. Ask "Explain this fault code." → the answer arrives **in the same
   conversation** (the backend keeps the last 12 messages server-side; the app
   never re-sends your transcript).

### 4.5 Empty and oversized messages
9. Press send with an empty composer → nothing is sent, the button is disabled,
   and if you force it you get *"Type a question first."*
10. Paste ~4100 characters → a counter appears (`4,1xx / 4,000`) in red and the
    error *"Messages can be up to 4,000 characters."*; send is blocked.

### 4.6 Network failure and retry (the important one)
11. Turn the phone's **airplane mode on** (or stop the backend).
12. Send a question.
13. Expect: your question stays on screen, **no assistant bubble is invented**,
    and a red notice appears: **"No answer produced"** + *"Cannot reach the
    3awedlou server. Check your connection."* + a **Retry** button.
14. Turn airplane mode off → tap **Retry** → the answer arrives and the notice
    disappears. Your question is **not** duplicated in the thread.
    (Retries are always explicit — the app never re-POSTs on its own, because a
    duplicate POST would append the question to the conversation twice and spend
    your tokens again.)

### 4.7 Assistant switched off
15. Set `AGENT_ENABLED=false` in the backend `.env.local`, clear the cache,
    restart the backend.
16. Send a message → the thread is replaced by **"Assistant not available"**
    ("The AI assistant is switched off on this server right now…") and the
    composer disappears. Put it back to `true` and restart to continue.
    *The app cannot know the flag in advance — there is no probe endpoint, and
    probing would spend your own rate-limited budget.*

### 4.8 Daily usage limit
17. Set `AGENT_DAILY_TOKEN_CAP=1` in `.env.local`, clear the cache, restart.
18. Send a message → **"Daily AI limit reached"** + *"Daily AI usage limit
    reached. It resets at 00:00 UTC."* The composer stays usable but a warning
    banner shows while the retry window from `Retry-After` is active.
19. Restore `AGENT_DAILY_TOKEN_CAP=200000` afterwards.
    (Verified live: the server answers `429` with `Retry-After: 60`.)

### 4.9 Stale / missing telemetry (the honesty check)
20. Stop telemetry (stop the MQTT publisher / the simulator).
21. After **2 minutes** of no new sample the data strip shows `data 2m old ·
    stale` (amber) and an amber banner appears: *"Telemetry is 2m old. Values the
    assistant reads may no longer match the machine…"*
22. After **10 minutes** it becomes `very stale` (red) and the banner says
    *"Telemetry is more than 10 minutes old…"*
23. With no telemetry at all the strip reads **"no telemetry yet"** and the
    assistant's answers say so — the app never turns a missing value into `0`.
24. Dismiss the banner with the ✕; it comes back on the next stale turn.

### 4.10 Theme, layout and keyboard
25. Toggle the theme from the header → the assistant follows light/dark (all
    colours come from the existing tokens).
26. Use it on the smallest phone you have: bubbles stay inside the screen, the
    composer sits above the keyboard, no horizontal scrolling.
27. Scroll up while an answer is arriving: the list must **not** yank you back
    down. It only auto-scrolls when you are already near the bottom or you just
    sent something.

### 4.11 Backgrounding the app mid-turn
28. Send a question, then switch apps immediately and come back after it lands.
    The answer is there.
    *Deliberate design decision:* the app does **not** abort the turn when it is
    backgrounded (the earlier design note proposed pausing). Aborting would throw
    away an answer whose tokens were already reserved — so the request is left to
    finish. Updated in `docs/ai-agent-ui.md`.

### 4.12 Deleting
29. Tap the 🗑 in the header → **"Delete this conversation?"** → **Delete**.
    Expect a toast "Conversation deleted" and an empty thread; a follow-up
    question starts a fresh conversation. (The server soft-deletes it; deleting
    it again is a 404.)
30. **Delete all history** → confirm → *"Conversations deleted"*; the backend
    reports how many were removed.

### 4.13 Read-only proof
31. Ask it to do something physical, e.g. *"Turn the heater off."*
32. Expect: the model may *explain* that it cannot, or the backend's tool guard
    rejects the call — either way **no machine command is ever sent**. The
    assistant code imports only `api/agent.ts`: there is no import of the
    machine/command API anywhere in `pages/AgentChatPage.tsx`,
    `lib/useAgentChat.ts`, `api/agent.ts` or `components/agent/*`, and the tool
    list the backend exposes is read-only (five read tools, no write tool).
    Check it yourself:

    ```bash
    grep -rn "sendMachineCommand\|/commands" pages/AgentChatPage.tsx lib/useAgentChat.ts api/agent.ts components/agent/ || echo "no machine-command reference (expected)"
    ```

## 5. Verify it without a phone

### 5.1 The three static checks

```bash
cd PET-Recycling-Filament-System-Mobile
npm run typecheck                    # exit 0
npm test                             # 29 tests, exit 0
npx expo export --platform android --output-dir dist   # exit 0 (Android bundle)
```

### 5.2 The live backend contract, by hand

```bash
# 1. token
TOKEN=$(curl -s -X POST http://127.0.0.1:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"anouer@3awedlou.app","password":"3awedlou-dev"}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

# 2. one turn (200)
curl -s -D- -X POST http://127.0.0.1:8000/api/agent/chat \
  -H 'Content-Type: application/json' -H "Authorization: Bearer $TOKEN" \
  -d '{"message":"What is the latest telemetry for my machine?"}'

# 3. same conversation (200, same conversationId)
#    NOTE: this exact call was NOT exercised live in this session (the harness
#    sent an empty id, which the server answered with 404 AGENT_NOT_FOUND — the
#    id above must come from your own step 2 response).
curl -s -X POST http://127.0.0.1:8000/api/agent/chat \
  -H 'Content-Type: application/json' -H "Authorization: Bearer $TOKEN" \
  -d '{"conversationId":"<id from step 2>","message":"Show recent machine events."}'

# 4. delete one / delete all
curl -s -X DELETE "http://127.0.0.1:8000/api/agent/conversations/<id>" -H "Authorization: Bearer $TOKEN"
curl -s -X DELETE http://127.0.0.1:8000/api/agent/conversations -H "Authorization: Bearer $TOKEN"
```

Expected shapes (this is exactly what the app parses):

```json
{ "success": true,
  "data": { "conversationId": "01a1475e-…",
            "message": { "id": "01a1475e-…", "role": "assistant",
                         "content": "…", "toolCalls": [], "createdAt": "2026-10-17T02:59:17+02:00" } },
  "meta": { "usage": { "input": 10, "output": 10 } } }
```

```json
{ "success": true, "data": { "deleted": true, "conversationId": "01a1475e-…" } }
{ "success": true, "data": { "deleted": true, "count": 0 } }
```

### 5.3 Replay a real response through the app's parser

The app's contract logic is plain TypeScript with no React Native imports, so a
real backend response can be replayed through it:

```bash
cd PET-Recycling-Filament-System-Mobile
npm test --silent            # also compiles .test-build/lib/agentContract.js

# save a real 200 body, then:
node -e '
  const c = require("./.test-build/lib/agentContract.js");
  const body = JSON.parse(require("fs").readFileSync("turn.json","utf8"));
  const t = c.parseChatResponse(body.data, body.meta);
  console.log(t.conversationId, "|", t.content, "|", JSON.stringify(t.usage));
'
```

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| "Assistant not available" in the app | `AGENT_ENABLED` is false (or set only as a shell variable) | §2.1 — put it in `.env.local`, `php bin/console cache:clear`, restart |
| "Something went wrong. Please try again." | 500 from the backend | Usually missing agent tables → §2.2 |
| "The assistant could not generate a response" | `503 AGENT_LLM_UNAVAILABLE` | No/invalid `ANTHROPIC_API_KEY` → §2.3 |
| "Cannot reach the 3awedlou server" | Wrong `EXPO_PUBLIC_API_BASE_URL`, firewall, or backend on `127.0.0.1` | §2.4, §3.1, and `npm start -- -c` after changing `.env` |
| App shows old data after editing `.env` | Expo embeds `EXPO_PUBLIC_*` at start | `npm start -- -c` |
| Answers look like `ECHO …` | The backend is running in `APP_ENV=test` (deterministic stub) | Run the dev environment for real answers |
| Assistant answers "not reported" everywhere | The machine has not reported telemetry | Expected — §4.9; the app never invents values |
| `npm test` fails with a TypeScript error | The pure modules no longer compile | Fix the type error; `.test-build/` is disposable output |
| Answers are slow (>30 s) | The provider round trip plus up to 4 tool rounds | Expected; the app gives up after 120 s and offers Retry |

## 8. Security notes

- The phone **never** sees `ANTHROPIC_API_KEY` (or any other key). It calls your
  API with the user JWT from `expo-secure-store`.
- Ownership is enforced server-side: the app can only act on its own
  conversations. A foreign or deleted id behaves exactly like a missing one.
- **No machine command path exists** in the assistant code: the chat module
  imports only `api/agent.ts`; there is no import of the machine/command API.
- Assistant text is **untrusted** and rendered as text only (React Native has no
  HTML layer, no Markdown parser, no auto-linking, no `dangerouslySetInnerHTML`),
  so model output cannot become UI or execute anything.
- Server error payloads are never shown: the app maps codes to its own fixed
  messages (a 500 shows "Something went wrong", not SQL or a stack trace).
- POSTs are never retried automatically — a retry is always a tap by you.
- Nothing about the chat is persisted to `AsyncStorage`; the transcript lives in
  screen state only (see the limitation below).
- Multi-user isolation assumption: the same machine may be visible to a second
  account only if the backend grants it — the app never widens that.

## 9. Known limitations (honest list)

1. **No conversation history endpoint** on the backend, so the transcript is
   screen state: leaving `AgentChat` or reloading the app clears it, and the next
   message starts a new conversation. The app never claims otherwise.
2. **No structured per-turn staleness.** Tool results carry no timestamp
   (`toolCalls: [{name, summary}]`), so freshness comes from the machine's newest
   reported sample via the normal machine API, plus an always-visible warning
   that answers can be out of date.
3. **A failed turn leaves its question stored server-side** (the backend persists
   the user message before calling the provider), so a Retry appends it to the
   server-side context again. The visible transcript stays clean.
4. **No cancel/stop button** — the API is non-streaming and the backend keeps
   working after a disconnect, so a client-side cancel would be a lie. Only
   leaving the screen aborts the request.
5. **The per-user message rate limit does not actually enforce anything** under a
   per-request SAPI (see §2.3). The daily token cap is the real limit.
6. **No streaming**: answers arrive in one piece.
7. **The disabled flag is discovered on first use** — there is no probe endpoint,
   so the entry points are always visible.

Good next steps (backend): a conversation-history endpoint, structured
staleness on tool results, idempotency for a failed turn, and a durable rate
limiter store.
